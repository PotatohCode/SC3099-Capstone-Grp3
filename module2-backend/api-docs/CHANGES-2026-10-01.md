**What each module needs to do to work with the backend.** One row per task,
each linked to the details. Only open tasks are listed; finished ones move to
[Completed tasks](CHANGELOG.md#completed-team-tasks). Why things changed:
[CHANGELOG.md](CHANGELOG.md). How endpoints behave:
[API-CONVENTIONS.md](API-CONVENTIONS.md) and your `API-FOR-*.md`.

**Last updated:** 2026-10-23 (M1 PR #4 `52112ca` reviewed: 10 tasks done,
one new, optional). Status is as of `main`, plus open branches where noted.

**Getting the latest backend:**
```bash
git pull
docker compose up -d --build backend   # rebuild: a stale image serves old code; migrations run on start
```

**Priority:** **Must** = broken or graded until done · **Should** = needed for
correct behaviour or to unlock a backend feature · **Decide** = group decision
first · Optional · FYI = no action, just be aware.

## When you're done: tell the backend owner

These backend switches are **off** until your side ships, then get turned on:

| Switch | Turned on (`flag`) after | Status |
|---|---|---|
| `CONSENT_ENFORCEMENT` | M1 sends consent | M1 done (`52112ca`); backend to test, then turn on |
| `DEVICE_BINDING_ENFORCEMENT` | M1 uses a random per-install fingerprint **and keeps it when taken** | Stays off unless M1 does the optional "Keep the device ID when it's taken" |
| `LIVENESS_CHALLENGE_ENFORCEMENT` | M1 sends challenge bursts **and** M3 returns `challenge_passed` | M1 done (`52112ca`); waiting on M3 |

Problems: contact the Module 2 (backend) owner with the `X-Request-ID`
header of the failing response.

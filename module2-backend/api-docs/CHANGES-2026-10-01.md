# Module 2 Backend — Changes & Integration Baseline

**For:** Module 1 (Frontend), Module 3 (Face Recognition), Module 4 (Observability Dashboard)
**Applies to:** `main` once `backend/deploy-robustness` is merged (it includes everything below)
**Last updated:** 2026-10-01

This is the **single reference** for how the backend behaves now, what
changed since the original course spec, and **what each module needs to do**.
Build against this document. Further backend changes are planned to be small
and additive; anything that changes behaviour will be added here.

**Why these changes happened**

- The course re-released its starter files and sent a clarification email
  with **new graded requirements**: account lockout, Singapore-only
  check-ins, and higher per-IP rate limits.
- A review against the briefing PDFs and spec found **security and privacy
  gaps** that the hidden tests target (40 hidden tests = 30% of the grade):
  GPS spoofing, replay attacks, privacy audits, and stress testing with 100
  concurrent users.
- Load testing found that **~100 simultaneous users made the backend fail**,
  and that **a fresh database never got its tables**. Both are fixed.

**Status:** the course's public test suite passes in full on the backend
(96 passed, 1 skipped by the course; 92/92 points) after every change listed
here.

## 2. Updating your local stack

```bash
git pull
docker compose up -d --build
```

That's it. **Database migrations now run automatically** when the backend
starts, so no more `alembic upgrade head`.

What you'll notice:
- **The backend has a health check.** `docker compose ps` shows it as
  `(healthy)`, and the **frontend and dashboard now wait** for that before
  starting (a few seconds after `up`).
- **On a fresh database** (e.g. after `docker compose down -v`), the backend
  creates every table itself on first start.

**If something looks wrong:**
- `curl localhost:8000/health` shows which part is down (see
  [3.5](#health-check)).
- Errors include an `X-Request-ID` response header. Quote it when reporting
  a backend problem.

## 3. What changed, and why

### 3.1 Sign-in and accounts

#### Account lockout (graded)

**Why:** course clarification email, "after 10 consecutive failed password
attempts … further login attempts must return HTTP 429".

`POST /api/v1/auth/login`
- After **10 consecutive wrong passwords on one account**, it's locked for
  **15 minutes**.
- While locked, **every** login returns `429`, **even with the correct
  password**:
  ```http
  HTTP/1.1 429 Too Many Requests
  Retry-After: 900

  { "detail": "Account locked due to too many failed login attempts", "code": "ACCOUNT_LOCKED" }
  ```
  `Retry-After` = seconds left (≤ 900). It's readable from browser code
  (CORS `Access-Control-Expose-Headers`).
- Attempts 1–10 return the normal `401 INVALID_CREDENTIALS`; the 11th is the
  first `429`.
- **Per account**, not per IP or device. A successful login resets the
  count, so it must be 10 failures **in a row**.
- An admin can unlock early: `PATCH /api/v1/admin/users/{id}/activate`.
- Unknown emails can't be locked; they keep returning `401`.

#### Rate limits

**Why:** the course email asked for per-IP limits to be raised, because
graders run every test from one IP.
- Per IP: login failures and registrations are **100,000/hour** (were 60
  and 300). A plain `429 RATE_LIMITED` on login is now practically
  unreachable, so **a `429` from login means `ACCOUNT_LOCKED`**.
- Per user (unchanged): check-ins **10/minute**, all API calls
  **1000/hour**.

#### Logout and token revocation

**Why:** JWTs used to stay valid until they expired (1 h access, 7 days
refresh), even after "logout". A stolen refresh token could be replayed
for a week.

`POST /api/v1/auth/logout`, new
- Body (optional): `{ "refresh_token": "..." }`. Header (optional):
  `Authorization: Bearer <access token>`.
- Revokes **whichever of the two you send**; both is best. From then on
  they're rejected everywhere (`401`), including `/auth/refresh`.
- Always returns **`204`**, even for tokens that are already invalid, so
  it's safe to call twice. Logging in again works normally. Other sessions
  of the same user are unaffected.
- Tokens now carry a unique `jti` claim. Older tokens without one can't be
  revoked; they just expire.
- **Refresh-token rotation** (single-use refresh tokens) exists but is
  **off**. If it's ever turned on, a refresh token works once, so always
  store the new one you get back. The frontend already does.

#### Account deletion (right to deletion)

**Why:** briefing privacy principle "right to deletion"; SECURITY-REQUIREMENTS
"user PII: 30 days after deletion".

`DELETE /api/v1/users/me`, new
```json
// request body
{ "password": "<current password>" }
// 202 Accepted
{ "message": "Account deactivated; personal data will be removed on the scheduled date",
  "scheduled_deletion_at": "2026-10-31T13:07:48" }
```
- The password is required, so a stolen access token alone can't delete an
  account. A wrong password returns **`403 PASSWORD_INCORRECT`**, not 401,
  so clients don't mistake it for an expired session.
- The account is **deactivated immediately**: all of its tokens stop
  working, and login returns `403 ACCOUNT_DISABLED`. Personal data is
  **anonymised automatically** after 30 days.
- Admin version: `DELETE /api/v1/users/{id}` (no password). An admin
  `PATCH /admin/users/{id}/activate` **cancels** a pending deletion.

### 3.2 Check-ins

#### Validation order

`POST /api/v1/checkins/` checks in this order and stops at the first
failure:

```
429 RATE_LIMITED (10/min per student)
→ 413 IMAGE_TOO_LARGE
→ 404 SESSION_NOT_FOUND
→ 403 NOT_ENROLLED
→ 400 SESSION_NOT_ACTIVE
→ 400 SESSION_WINDOW_CLOSED
→ 400 ALREADY_CHECKED_IN
→ 403 CONSENT_REQUIRED      (only if CONSENT_ENFORCEMENT=reject; off by default)
→ 403 OUTSIDE_SINGAPORE
→ face/liveness calls to Module 3 → risk scoring → 201 (approved | flagged | rejected)
```

**A `201` doesn't mean "approved".** Check `status`. Rejected check-ins are
stored (`201` with `status: "rejected"`) and can be appealed.

#### Singapore-only check-ins (graded)

**Why:** course clarification email.

A check-in gets **`403 OUTSIDE_SINGAPORE`** if **either**:
- the GPS is outside Singapore (box: lat 1.15–1.48, lon 103.59–104.10), **or**
- the client IP is a **public IP located outside Singapore** (offline
  GeoIP database).

Private/local IPs (`10.x`, `172.16–31.x`, `192.168.x`, `127.x`, `::1`) count as
on-campus and are allowed. So are public IPs the database can't place.

```json
{ "detail": "Check-in only allowed from within Singapore", "code": "OUTSIDE_SINGAPORE" }
```
**Nothing is stored**, so the student can retry (e.g. after switching off a
VPN) without hitting `ALREADY_CHECKED_IN`. The attempt is audited.

**Client IP rule:** the backend uses the **first `X-Forwarded-For` address**
if present, otherwise the TCP connection address. The same IP is used for
audit logs, rate limits, the Singapore check and the call to Module 3. In
our docker-compose setup nothing sets that header, so browser traffic shows
as a private Docker IP and passes the IP part. The GPS part always applies.

#### Face and liveness requirements are enforced

**Why:** sessions always had `require_face_match` / `require_liveness_check`
settings, but they were ignored, so a **different person's face was
approved** on a session that required a match.

| Session requires | Situation | Outcome | `risk_factors` entry |
|---|---|---|---|
| Face match (or the course's `require_face_recognition`) | Face **doesn't match** the enrolled one | `rejected` | `face_match_failed` |
| Face match | Couldn't compare: no photo, no enrolled face, or face service down | at most `flagged` | `face_match_unverified` |
| Liveness check | Liveness **failed** | `rejected` | `liveness_failed` |
| Liveness check | No usable result: no photo, no face found, or service down | at most `flagged` | `liveness_unverified` |

The "unverified" cases never auto-approve. They go to instructor review
instead of being rejected, so a face-service outage doesn't reject genuine
students.

#### Suspicious-activity detection

**Why:** hidden tests cover GPS spoofing, replay attacks and proxy
sign-in.

| `risk_factors` type | Triggered when | Outcome |
|---|---|---|
| `replay_suspected` | The **same student** sends byte-identical photo data they used in an earlier check-in | `rejected` |
| `gps_spoof_suspected` | `location_accuracy_meters` < 1 m (mock-location tools often send 0) | at most `flagged` |
| `rapid_succession` | The same `device_fingerprint` checked in a **different student** in the last 10 minutes (one phone signing in friends) | at most `flagged` |
| `impossible_travel` | Implied speed from the student's previous check-in > 250 km/h | adds 0.30 to the score |
| `unusual_time` | More than 15 minutes after `scheduled_start` | Informational only |

Only **hashes** of the photo and of the device fingerprint are stored, never
the photo or the raw fingerprint. Replay detection is per student, so
different students who happen to use the same sample image aren't affected.

#### Coordinates are stored at 4 decimal places

**Why:** briefing, "location data … stored with limited precision".

Check-ins **store and return** `latitude`/`longitude` rounded to 4 decimals
(about 11 m). The geofence, Singapore check and impossible-travel check use
the **full-precision position you send**, so keep sending full precision.

#### Upload size limits

**Why:** an unlimited image upload is held in memory, hashed and forwarded
to Module 3, which makes it an easy way to tie up the service.

| Limit | Response |
|---|---|
| `liveness_challenge_response` or face-enroll `image` over **10,000,000 base64 characters** (~7.5 MB image) | `413 IMAGE_TOO_LARGE` |
| Any request body over **15 MB** (by `Content-Length`) | `413 REQUEST_TOO_LARGE` (refused before reading) |

A normal camera JPEG (0.1–2 MB) and all course sample images are well under
these limits.

#### Consent and device-binding enforcement (built, switched off)

**Why:** the briefing says consent must be given before check-in, and that
check-ins from unknown devices should be flagged. Both depend on frontend
changes that haven't shipped, so they're built now but **off**.

| Setting | Values (default **`off`**) | Effect when on | Turned on after |
|---|---|---|---|
| `CONSENT_ENFORCEMENT` | `off` / `flag` / `reject` | `flag`: a student without camera **and** location consent → `consent_missing`, at most `flagged`. `reject`: `403 CONSENT_REQUIRED` | Frontend sends consent ([M1 §C](#c-should-send-consent-to-the-backend)) |
| `DEVICE_BINDING_ENFORCEMENT` | `off` / `flag` | On a course with `require_device_binding` (the default), a device not registered to the student → `device_unbound`, at most `flagged` | Frontend fingerprint fix ([M1 §B](#b-should-fix-the-device-fingerprint)) |

We'll announce here when each is switched on (planned: `flag`, never
`reject`, because the course's own tests check in without consent).

### 3.3 How a check-in outcome is decided

1. **Base score.** If a photo was sent and Module 3 answers, its
   `/risk/assess` score is used. Otherwise the backend uses a local formula
   (liveness, device, distance).
2. **Signal weights are added**, e.g. `device_unknown` +0.10,
   `geo_out_of_bounds` +0.15, `impossible_travel` +0.30. The score is capped
   at 1.0.
3. **Decision:**
   - a **hard-reject signal**, or score **≥ 0.7** → `rejected`;
   - else score **≥ `risk_threshold`** (default 0.5), or a **review-only
     signal** → `flagged`;
   - else → `approved`.

**A check-in without a photo scores about 0.68,** so it's always `flagged`,
never auto-approved, because a missing liveness result counts as full risk.
To be auto-approved a student needs a photo, and on face-required sessions
an enrolled face.

#### Risk bands

Every check-in response, and every check-in list item, now includes
**`risk_level`**, computed with the same function the backend uses to
decide:

| `risk_level` | Score | Meaning |
|---|---|---|
| `LOW` | < 0.3 | Auto-approve |
| `MEDIUM` | 0.3 – 0.5 | Auto-approve, logged |
| `HIGH` | 0.5 – 0.7 | Flag for review |
| `CRITICAL` | ≥ 0.7 | Auto-reject |

Signal **severity** follows the same idea: **`"critical"` means "this
signal alone rejected the check-in"**. `impossible_travel` is `"high"` and
only adds score.

### 3.4 Courses and sessions

#### `PUT /courses/{id}` is admin-only

**Why:** the re-released API spec changed it from "admin or course
instructor" to "admin only". Instructors get `403 INSUFFICIENT_PERMISSIONS`,
even for their own course. They can **still** manage its enrollments and
sessions and view its stats.

#### Sessions must start in the future

**Why:** API spec, POST /sessions/ validation.

Creating a session whose `scheduled_start` is **more than 5 minutes in the
past** → `400 INVALID_SCHEDULE` ("scheduled_start must be in the future").
The grace window keeps "start now" working. Editing an existing session
isn't affected.

#### `risk_threshold` above 0.7

Allowed (the spec range is 0.0–1.0), but **scores ≥ 0.7 are always
rejected**, whatever the threshold. A threshold above 0.7 just means
nothing gets flagged: below 0.7 is approved, 0.7 and above is rejected.

### 3.5 API-wide behaviour

#### Pagination

List endpoints accept at most **`limit=100`**. Larger values are **capped,
not rejected**: you get 100 items and `"limit": 100`. The audit log keeps
its documented maximum of 1000.

#### Request IDs

Every response, including errors, has an **`X-Request-ID`** header
(readable from browser code). Send your own (letters, digits, `. _ -`, up
to 64 characters) to trace a request, or quote the returned one when
reporting a bug. It appears in the backend's error logs.

#### Health check

`GET /health` now checks the database and Redis:

| State | Response |
|---|---|
| All good | `200 {"status":"healthy","service":"backend","database":"ok","redis":"ok"}` |
| Redis down | `200 {"status":"degraded", ..., "redis":"unavailable"}`. The backend still works (rate limiting is skipped) |
| Database down | `503 {"status":"unhealthy", ..., "database":"unavailable"}` |

### 3.6 Privacy and audit

- **Audit log is append-only in the database itself.** `UPDATE`, `DELETE`
  and `TRUNCATE` on `audit_logs` are refused, even with direct SQL.
- **Retention runs automatically** (shortly after startup, then hourly):
  check-in location and face data are anonymised 30 days after the check-in,
  and deleted accounts 30 days after the request. Each run is audited
  (`retention_sweep_run`, `"trigger": "scheduled"`).
- **No raw images or fingerprints are stored**, only hashes (see 3.2).
  Geo-rejection audit entries don't contain coordinates.
- **Free text is HTML-escaped when stored**, including appeal reasons and
  review notes (previously missed). A name like `<script>` comes back as
  `&lt;script&gt;`.
- **`security_violation` audit events** are written for suspicious
  activity, next to the specific event, so there's one action to alert on.
  See [5.4](#54-audit-events).
- **CSV export is protected against formula injection.** Cells starting
  with `= + - @` get a leading `'`, so a malicious name can't run as an
  Excel formula. JSON export is unchanged.

### 3.7 Reliability and performance

- **100+ concurrent users:** fixed. Previously ~100 simultaneous requests
  stalled for 30 s and 8–40% failed with `500`. Now 100 and 150 concurrent
  registrations, logins and check-ins all succeed, typically within 1 s.
- **Faster:** login/registration (bcrypt cost 10, the spec minimum), and
  session lists (about 7× faster under load).
- **Automatic migrations and a health check** (see [section 2](#2-updating-your-local-stack)).
- **Face service resilience:** if Module 3 times out or returns 5xx, the
  backend stops calling that endpoint for 30 s and scores locally. A
  **4xx** (Module 3 rejecting one request) now only affects that request.

## 4. Module guides

### Module 1 — Frontend

#### A. Must: fix the backend address baked into the build

`docker-compose.yml` passes `NEXT_PUBLIC_API_URL=http://192.168.64.4:8000`
(and the face URL) as **build args**, and adds `http://192.168.64.4:3000`
to the backend's `CORS_ORIGINS`. Next.js bakes `NEXT_PUBLIC_*` into the
JavaScript at build time, so on any other machine the site calls an
address that doesn't exist and hangs (e.g. "Creating account…" forever).

**Fix:** default to localhost and allow an override, e.g.
`NEXT_PUBLIC_API_URL: http://${PUBLIC_HOST:-localhost}:8000`, and the same
for `CORS_ORIGINS`. Testing from a phone then means setting `PUBLIC_HOST`
to your own LAN IP. Change the frontend and CORS lines **in the same
commit**, or browsers will be blocked.

#### B. Should: fix the device fingerprint

`lib/utils/device-fingerprint.ts` hashes only browser traits (user agent,
screen, timezone, platform, language) and keeps the result in
`sessionStorage`. Students with the same phone model and browser get **the
same fingerprint**:
- the backend allows one owner per fingerprint, so everyone after the first
  gets `400 DEVICE_FINGERPRINT_TAKEN` (silently swallowed in
  `AuthContext.registerDeviceOnce`), and their check-ins carry
  `device_unknown`;
- two such students checking in within 10 minutes are flagged as
  `rapid_succession` (shared device).

**Fix:** `crypto.randomUUID()` once per install, stored in `localStorage`.
**Unlocks:** `DEVICE_BINDING_ENFORCEMENT=flag`.

#### C. Should: send consent to the backend

Camera and location consent are tracked only in the browser
(`consent-tracker.ts`). The backend never hears about them, so
`camera_consent`/`geolocation_consent` stay `false`.

**Fix:** when the student grants a permission, call
```http
PUT /api/v1/users/me
{ "camera_consent": true, "geolocation_consent": true }
```
(only the field that changed is fine). **Unlocks:** `CONSENT_ENFORCEMENT=flag`.

#### D. Should: add face enrolment

Nothing in the website calls `POST /users/me/face/enroll`, so no student has
an enrolled face. On sessions that require face matching, every check-in is
`flagged` (`face_match_unverified`) and none can be auto-approved.

**Flow:** camera consent → `PUT /users/me {camera_consent: true}` →
capture a frame → `POST /users/me/face/enroll { "image": "<base64, no data: prefix>" }`.
Responses: `200` enrolled; `400 CAMERA_CONSENT_REQUIRED`;
`400 NO_FACE_DETECTED`; `413 IMAGE_TOO_LARGE`; `503` face service down.

#### E. Error handling to add

| Response | Show the student | Notes |
|---|---|---|
| Login `429 ACCOUNT_LOCKED` | "Too many failed sign-in attempts. This account is locked for N minutes." | `N = Math.ceil(retryAfterSeconds / 60)`. `http-client.ts` already puts `Retry-After` in `error.rateLimit.retryAfterSeconds`. Don't say "wrong password": they may have typed the right one |
| Check-in `403 OUTSIDE_SINGAPORE` | "Check-in is only available within Singapore. If you're using a VPN, turn it off and try again." | Tell it apart from `403 NOT_ENROLLED` by `code`. **Allow retry**: nothing was saved |
| Check-in `201` with `status: "rejected"` / `"flagged"` | Show the outcome and offer **Appeal** for rejected/flagged | `rejected` is a stored result, not an error |
| `403 CONSENT_REQUIRED` | Ask for camera + location permission | Only if consent enforcement is ever set to `reject` |
| `413 IMAGE_TOO_LARGE` | "Photo too large, please retake" | Shouldn't happen with normal capture |
| `DELETE /users/me` `403 PASSWORD_INCORRECT` | "Password is incorrect" | Deliberately not 401, so your 401 → refresh → logout logic doesn't fire |

#### F. Other notes

- **Take a fresh photo per check-in.** Re-sending a cached image (e.g. from
  the offline queue for a different session) is rejected as
  `replay_suspected`.
- **Send the real `location_accuracy_meters`** from the Geolocation API.
  Don't default to `0`; under 1 m is treated as a mocked location.
- **Risk badge:** `components/StatusBadge.tsx` uses three levels, so a
  CRITICAL score shows as "High (0.77)" next to "Rejected". Use the new
  `risk_level` field, or add `≥ 0.7 → "Critical"`.
- **Logout:** call `POST /auth/logout` with the refresh token (and access
  token header) before clearing local tokens. It always returns 204.
- **Testing locations:** use NTU (`1.3483, 103.6831`). Devtools locations
  outside Singapore get `403`.
- **If you add a proxy** (Next.js rewrites, nginx), make it set
  `X-Forwarded-For` to the real client IP. Never set it from browser code.
- **Coordinates come back rounded** to 4 decimals (display only).

### Module 3 — Face Recognition

**Your API contract is unchanged.** We call `/face/enroll`, `/face/verify`,
`/liveness/check` and `/risk/assess` with the same bodies and read the same
fields.

#### A. Should: private IPs are not VPNs

`detect_vpn_proxy()` gives `10.x`, `172.16–31.x`, `192.168.x`, `127.x` and
`::1` a 0.7 VPN confidence. Inside Docker, every request arrives from a
private address, and the course rule (enforced by the backend) treats
private IPs as **on-campus**. Genuine check-ins therefore get extra network
risk from your score. **Suggested:** treat private and loopback addresses as
neutral, and keep the user-agent keyword check.

#### B. Should: expect ~100 concurrent calls

The backend now handles 100+ simultaneous check-ins, and each one with a
photo calls `/liveness/check`, `/face/verify` (if enrolled) and
`/risk/assess`. The backend waits **at most 5 s** per call, then scores
locally. Load-test with ~50–100 parallel requests: MediaPipe in one process
may be the bottleneck.

#### C. Should: add metrics

`module4-observability/prometheus.yml` scrapes `face-recognition:8001/metrics`
and gets 404. Adding `prometheus_client` with a `GET /metrics` route (e.g.
request latency, enroll/verify/liveness counts) makes the target healthy.

#### D. Optional: dependency caps and base64 whitespace

- The re-released starter caps `opencv-python<4.12` and `numpy<2` next to
  the `mediapipe==0.10.18` pin you already have. Both caps are missing from
  `module3-face-recognition/requirements.txt` and the root
  `requirements-test.txt`.
- A base64 image containing line breaks makes `/face/verify` report a
  mismatch. Browsers don't add them, but stripping whitespace before
  decoding makes it robust.

#### E. No action: face enroll status codes

`/face/enroll` returns `201` with `enrollment_successful: false` for no
face or no consent (the spec text says 400). **Keep it.** The course's
public tests accept both forms, and the backend converts it into a proper
`400` for users. If you ever change it to 400, tell us first: the backend
handles a 4xx correctly now, but the docs would need updating.

#### What the backend sends you (for reference)

- `ip_address` in `/risk/assess` = the first `X-Forwarded-For` address or
  the connection address (normalised; may be IPv6).
- `geolocation` is sent only when the client provided
  `location_accuracy_meters` (your schema requires `accuracy`).
- Check-ins rejected for location (`OUTSIDE_SINGAPORE`), size (413) or
  earlier validation **never reach you**.

### Module 4 — Observability Dashboard

#### A. Must: session tiles read the wrong fields

`app/main.py` (lines ~253 and ~296) reads `flagged_count` and
`flagged_checkins` from `GET /stats/sessions/{id}`. The backend returns
counts inside **`by_status`**, e.g. `by_status.flagged`, so those tiles
always show 0.

#### B. Should: Grafana and OTel collector

- **Grafana** only reads `provisioning/datasources/*.yml` and
  `provisioning/dashboards/*.yml`. Our two files sit directly in
  `provisioning/`, so there are 0 datasources and 0 dashboards. Move them
  into those folders and add at least one dashboard JSON.
- **OTel collector:** `otel-collector-config.yml` uses the `logging`
  exporter, which `otel/opentelemetry-collector:latest` removed, so the
  container exits. Rename it to `debug` (`loglevel` → `verbosity`) or pin
  an older image.

#### C. Should: new signals to display

**Metrics** (`GET /metrics`, Prometheus):

| Metric | Labels | Use for |
|---|---|---|
| `security_violations_total` | `violation_type` | One "suspicious activity" panel/alert |
| `account_lockouts_total` | — | Brute-force attempts |
| `checkin_rejected_geo_total` | `reason` = `ip` / `gps` / `gps_and_ip` | Out-of-Singapore attempts |
| `login_failed_total` (changed) | — | Now also counts logins blocked by a lockout |

Labelled series only appear after their first occurrence. Treat "no data"
as 0 (`or vector(0)`).

**Audit and API data:**
- Check-in outcome audit events (`checkin_approved/_flagged/_rejected`) carry
  `details.risk_level`. Check-in API responses carry `risk_level` too. Use
  it rather than re-deriving bands, e.g. to show "auto-approved with
  logging" (MEDIUM).
- New audit actions are listed in [5.4](#54-audit-events). Geo-rejected
  check-ins create **no check-in row**, so they appear only in the audit log
  and metrics, not in `/stats/*` or exports.
- All `risk_factors` types are listed in [5.3](#53-risk-factor-types). Add
  any you chart.

**Example PromQL:**
```promql
sum by (violation_type) (increase(security_violations_total[1h]))
increase(account_lockouts_total[1h])
sum(increase(checkin_rejected_geo_total[1h])) / sum(increase(checkin_attempts_total[1h]))
```

#### D. Optional: small fixes

- `app/main.py` calls `/api/v1/sessions`, `/api/v1/checkins` and
  `/api/v1/courses` without a trailing slash, so each gets a 307 redirect
  first. Add the `/`.
- Page size: you request `limit=100`, which is the maximum (larger values
  are capped).
- When you build "create session": the start time must not be more than
  5 minutes in the past ([3.4](#sessions-must-start-in-the-future)).
  `risk_threshold` above 0.7 is allowed but makes "flagged" impossible.
- The audit log can't be edited or deleted, even with direct SQL. Don't
  build anything that needs to.

### 5.2 Error codes

Every error body is `{ "detail": "...", "code": "..." }` (422 validation
errors keep FastAPI's field list).

| Status | `code` | Where | Meaning |
|---|---|---|---|
| 400 | `INVALID_SCHEDULE` | `POST /sessions/` | Now also: start more than 5 min in the past |
| 403 | `OUTSIDE_SINGAPORE` | `POST /checkins/` | GPS or public IP outside Singapore; retry allowed |
| 403 | `PASSWORD_INCORRECT` | `DELETE /users/me` | Wrong password confirmation |
| 403 | `CONSENT_REQUIRED` | `POST /checkins/` | Only when `CONSENT_ENFORCEMENT=reject` |
| 413 | `IMAGE_TOO_LARGE` | check-in photo, face enrol | Image over 10,000,000 base64 chars |
| 413 | `REQUEST_TOO_LARGE` | any | Body over 15 MB |
| 429 | `ACCOUNT_LOCKED` | `POST /auth/login` | 10 consecutive failures; see `Retry-After` |

### 5.3 Risk factor types

`risk_factors` in check-in responses: `[{ "type": "...", "weight": 0.1 }]`.

| Type | Severity | Weight | Effect |
|---|---|---|---|
| `geo_out_of_bounds` | high (1–2× radius) / **critical** (> 2×) | 0.15 | > 2× geofence → **rejected** |
| `geo_accuracy_low` | low | 0.05 | Accuracy worse than 100 m |
| `device_unknown` | medium / low | 0.10 / 0.05 | Unregistered / registered but untrusted device |
| `impossible_travel` | high | 0.30 | > 250 km/h from the previous check-in |
| `liveness_failed` | **critical** | 0.25 | **rejected** |
| `liveness_unverified` | high | 0 | Liveness required but no result → at most flagged |
| `face_match_failed` | **critical** | 0.25 | Face-required session, wrong face → **rejected** |
| `face_match_unverified` | high | 0 | Face required but no comparison → at most flagged |
| `replay_suspected` | **critical** | 0.30 | Re-used photo (same student) → **rejected** |
| `gps_spoof_suspected` | medium | 0 | Accuracy < 1 m → at most flagged |
| `rapid_succession` | high | 0 | Device used by another student < 10 min ago → at most flagged |
| `unusual_time` | low | 0 | > 15 min after start; informational |
| `consent_missing` | medium | 0 | Only with `CONSENT_ENFORCEMENT=flag` |
| `device_unbound` | medium | 0 | Only with `DEVICE_BINDING_ENFORCEMENT=flag` |

**Critical = rejects on its own.**

## 6. Try it yourself

```bash
API=http://localhost:8000/api/v1

# Health
curl -s localhost:8000/health

# Lockout: 10 wrong passwords, then the right one -> 429 + Retry-After
for i in $(seq 1 10); do curl -s -o /dev/null -w "%{http_code} " -X POST $API/auth/login \
  -H 'Content-Type: application/json' -d '{"email":"you@test.edu","password":"wrong"}'; done
curl -i -X POST $API/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"you@test.edu","password":"<correct>"}'

# Singapore rule: a foreign IP -> 403 (needs an active session you're enrolled in)
curl -i -X POST $API/checkins/ -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'X-Forwarded-For: 8.8.8.8' \
  -d '{"session_id":"<id>","latitude":1.3483,"longitude":103.6831,"location_accuracy_meters":10,"device_fingerprint":"dev1"}'

# Logout, then the same token is rejected
curl -i -X POST $API/auth/logout -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d "{\"refresh_token\":\"$REFRESH\"}"
curl -i $API/users/me -H "Authorization: Bearer $TOKEN"      # -> 401

# Delete account (password required) -> 202
curl -i -X DELETE $API/users/me -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"password":"<current password>"}'
```

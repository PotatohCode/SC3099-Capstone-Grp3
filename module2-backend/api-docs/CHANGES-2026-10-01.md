## What changed

### 1. Account lockout after 10 failed logins

`POST /api/v1/auth/login`

- After **10 consecutive wrong passwords on the same account**, the account is
  locked for **15 minutes**.
- While it's locked, **every** login attempt returns `429`, **even with the
  correct password**:

  ```http
  HTTP/1.1 429 Too Many Requests
  Retry-After: 900

  { "detail": "Account locked due to too many failed login attempts", "code": "ACCOUNT_LOCKED" }
  ```

  `Retry-After` is the number of seconds left on the lock (at most 900).
- Attempts 1–10 still return the normal `401 INVALID_CREDENTIALS`. The 11th
  is the first `429`.
- The counter is **per account, not per device or IP**. Other accounts are
  unaffected, including ones on the same network.
- A successful login resets the counter to 0, so it has to be 10 failures
  *in a row*.
- An admin can unlock early with the existing
  `PATCH /api/v1/admin/users/{id}/activate`. It now also clears the lock.
- Unknown emails can't be locked (there's no account); they keep returning
  `401`.

### 2. Singapore-only check-ins

`POST /api/v1/checkins/`

A check-in is now rejected if **either**:
- the submitted GPS (`latitude`, `longitude`) is outside Singapore
  (bounding box: lat 1.15–1.48, lon 103.59–104.10), **or**
- the client IP is a **public IP located outside Singapore**.

Private and local IPs (`10.x`, `172.16–31.x`, `192.168.x`, `127.x`, `::1`)
count as on-campus and are allowed. Public IPs our offline GeoIP database
can't place are also allowed.

```http
HTTP/1.1 403 Forbidden

{ "detail": "Check-in only allowed from within Singapore", "code": "OUTSIDE_SINGAPORE" }
```

Where it sits in the validation order:

```
403 NOT_ENROLLED → 400 SESSION_NOT_ACTIVE → 400 SESSION_WINDOW_CLOSED
  → 400 ALREADY_CHECKED_IN → 403 OUTSIDE_SINGAPORE (new) → face/liveness → risk scoring → 201
```

- **No check-in record is created** when this happens. The student can retry
  once they're actually in Singapore (e.g. after switching off a VPN), and
  won't hit `ALREADY_CHECKED_IN`.
- The rejection is written to the audit log (see the [Dashboard section](#for-module-4--observability-dashboard)).

### 3. Client IP now honours `X-Forwarded-For`

The backend now works out "the client's IP" in one place, for every use: audit logs,
rate-limit keys, the Singapore check, and the `ip_address` sent to Module 3.

- If an `X-Forwarded-For` header is present, the **first** address in it is
  used (`X-Forwarded-For: <client>, <proxy1>, …`).
- Otherwise the TCP connection's address is used, as before.
- A malformed header is ignored, and the connection address is used instead.

Note: in our current `docker-compose` setup nothing adds this header, so the
backend still sees the Docker network address (a private `172.x` IP) for
browser traffic, the same as before.

### 4. `PUT /courses/{id}` is now admin-only

It was "admin, or the course's assigned instructor". The re-released API
spec makes it **admin only**. An instructor now gets
`403 INSUFFICIENT_PERMISSIONS`, even for their own course.

Instructors can **still** manage their course's enrollments and sessions,
and view its stats. Only editing the course record itself changed.

### 5. Per-IP rate limits raised

At the course's request (graders run all tests from one IP), the per-IP
limits on login failures and registration are now 100,000/hour (were
60 and 300). A plain `429 RATE_LIMITED` on login is now practically
unreachable, so in practice any `429` from login means `ACCOUNT_LOCKED`.
The per-user limits are unchanged: check-ins 10/minute, API 1000/hour.

### 6. Face match and liveness are enforced when required

Sessions have always accepted `require_face_match` and
`require_liveness_check`, but check-in processing didn't act on them, so a
different person's face could be approved on a session that required a
match. Now, on `POST /api/v1/checkins/`:

| Session requires… | Result | Check-in outcome | New `risk_factors` entry |
|---|---|---|---|
| Face match (or course `require_face_recognition`) | Face **doesn't match** the enrolled face | `rejected` | `face_match_failed` (weight 0.25) |
| Face match | Couldn't compare: no photo sent, no enrolled face, or face service down | at most `flagged` (never auto-approved) | `face_match_unverified` (weight 0) |
| Liveness check | No usable liveness result (no photo, no face found, service down) | at most `flagged` | `liveness_unverified` (weight 0) |
| Liveness check | Liveness **failed** | `rejected` (unchanged) | `liveness_failed` |

The "unverified" entries have weight 0: they stop auto-approval and send
the check-in to instructor review, but they don't change `risk_score`.
Sessions that don't require these checks behave exactly as before.

**Also:** `Retry-After` is now exposed to browser code (CORS
`Access-Control-Expose-Headers`), so the frontend can read the remaining
lock time on a `429`.

### 7. Suspicious check-ins are detected

`POST /api/v1/checkins/` now looks for common cheating patterns. The
response shape is unchanged; only `status` and `risk_factors` reflect them.

| New `risk_factors` type | When | Outcome |
|---|---|---|
| `replay_suspected` | The **same student** sends a byte-identical photo they already used in an earlier check-in (a replayed/captured image) | `rejected` |
| `gps_spoof_suspected` | `location_accuracy_meters` is under 1 m (mock-location tools often report 0) | at most `flagged` |
| `rapid_succession` | The same `device_fingerprint` checked in a **different student** within the last 10 minutes (one phone signing in friends) | at most `flagged` |
| `unusual_time` | Check-in more than 15 minutes after `scheduled_start` | Informational only, no effect |

- These new entries have **weight 0** (except `replay_suspected`), so they
  never raise `risk_score`. They only stop auto-approval and send the
  check-in to instructor review.
- Only a **hash** of the photo and of the device fingerprint is stored,
  never the photo or the raw fingerprint.
- `impossible_travel` keeps its weight but is now labelled severity
  `"high"`, not `"critical"`. Rule: **`"critical"` = the signal rejects on
  its own** (liveness failed, GPS > 2× geofence, face mismatch on a
  face-required session, replay).

### 8. Check-in coordinates are stored at 4 decimal places

Check-ins now **store and return** `latitude`/`longitude` rounded to 4
decimals (about 11 m), per the course privacy rule "location stored with
limited precision". The geofence distance, the Singapore check and
impossible travel still use the full-precision position you send, so keep
sending the full value.

### 9. Audit log changes

- New action **`security_violation`** (`success: false`) with
  `details.violation_type` = `account_lockout`, `outside_singapore`,
  `geo_out_of_bounds`, `liveness_failed`, `face_match_failed`,
  `replay_suspected`, `impossible_travel`, `gps_spoof_suspected` or
  `rapid_succession`. It's written next to the specific event, so you can
  alert on one action type.
- Check-in outcome events (`checkin_approved` / `checkin_flagged` /
  `checkin_rejected`) now include **`details.risk_level`**:
  `LOW` / `MEDIUM` / `HIGH` / `CRITICAL` (SECURITY-REQUIREMENTS bands).
- The audit log is now **append-only in the database itself**: `UPDATE`,
  `DELETE` and `TRUNCATE` on `audit_logs` are refused, even with direct SQL.
- The 30-day retention clean-up now **runs automatically** (shortly after
  start-up, then hourly). Each run writes a `retention_sweep_run` event
  with `details.trigger = "scheduled"`. The admin endpoint
  `POST /admin/retention/run` still works.
- Appeal reasons and review notes are now HTML-escaped when stored, like
  every other free-text field.

### 10. Small API changes

- **Page size:** list endpoints accept at most `limit=100`. Larger values
  are **capped, not rejected**: you get 100 items and `"limit": 100` in the
  response. The audit log keeps its documented maximum of 1000.
- **`X-Request-ID`:** every response (including errors) carries an
  `X-Request-ID` header, readable from browser code. Send your own (letters,
  digits, `. _ -`, up to 64 chars) to correlate a request, or quote the
  returned one when reporting a bug: it appears in backend error logs.

### 11. Performance and stability

Under about 100 simultaneous requests, the backend used to stall for 30 s
and fail 8–40% of them with `500`. That's fixed: 100 and 150 concurrent
registrations, logins and check-ins now all succeed, typically within 1 s.
Session lists are about 7× faster under load. No API change; this matters
for the hidden "100 concurrent users" stress tests.

## For Module 1 — Frontend

**Needed:**

1. **Login screen: handle `429` with `code: "ACCOUNT_LOCKED"`.**
   `lib/utils/http-client.ts` already rejects 429s with
   `error.rateLimit.retryAfterSeconds` set and never auto-retries, which is
   what we want. What's missing is a user-facing message. Suggested:
   > "Too many failed sign-in attempts. This account is locked for
   > *N* minutes."

   Use `Math.ceil(retryAfterSeconds / 60)` for *N*. Don't show it as "wrong
   password", because the user may have typed the right one.
   (`retryAfterSeconds` now has a value in the browser; it used to be
   `null` because the header wasn't exposed. See
   [section 6](#6-face-match-and-liveness-are-enforced-when-required).)
2. **Check-in flow: handle `403` with `code: "OUTSIDE_SINGAPORE"`.**
   Tell it apart from `403 NOT_ENROLLED` by `code`, not by status. Suggested:
   > "Check-in is only available within Singapore. If you're using a VPN,
   > turn it off and try again."

   Allow a **retry**: nothing was saved, so it isn't a duplicate check-in.

**Only if relevant:**

- **Course editing UI:** if you build one, show it to **admins only**.
  Instructors now get 403. (The frontend doesn't call `PUT /courses/{id}`
  today, so nothing breaks now.)
- **Adding a proxy** (Next.js rewrites, nginx, etc.) in front of the
  backend: make it **set `X-Forwarded-For`** to the real client IP.
  Otherwise every user appears to come from the proxy's IP, and the
  Singapore IP check becomes meaningless. Don't set this header from
  browser code.
- **Expect more `flagged`/`rejected` results** on sessions that require
  face match or liveness ([section 6](#6-face-match-and-liveness-are-enforced-when-required)).
  A student with no enrolled face on such a session will be `flagged`. A
  face-enrolment step in the UI (`POST /users/me/face/enroll`) would let
  them be auto-approved.
- **Testing with a spoofed location:** browser devtools location overrides
  outside Singapore will now get 403 on check-in. Use NTU
  (`1.3483, 103.6831`) for dev.

**New in sections 7–10:**

- **Fix the device fingerprint before many students use the app.**
  `generateDeviceFingerprint()` hashes only browser traits, so students on
  the same phone model and browser get the **same fingerprint**. With
  [section 7](#7-suspicious-check-ins-are-detected), the second such
  student checking in within 10 minutes is flagged as `rapid_succession`
  (shared device). Suggested fix: generate a random ID once per install
  (`crypto.randomUUID()`) and keep it in `localStorage`.
- **Always capture a fresh photo for each check-in.** Re-sending a
  previously captured image (e.g. from a cache or the offline queue, for a
  different session) is rejected as `replay_suspected`.
- **Send the real `location_accuracy_meters`** from the Geolocation API.
  Don't default it to `0`; anything under 1 m is treated as a possible
  mock location and flagged.
- **Coordinates come back rounded** to 4 decimals
  ([section 8](#8-check-in-coordinates-are-stored-at-4-decimal-places)).
  Display only; nothing to change.
- **When reporting a backend bug**, include the response's `X-Request-ID`
  header ([section 10](#10-small-api-changes)).

## For Module 3 — Face Recognition

**Your API contract is unchanged.** We call the same four endpoints with the
same request bodies, and read the same response fields.

What you may notice:

1. **`ip_address` in `POST /risk/assess`** is now the first
   `X-Forwarded-For` address when present, otherwise the connection address
   as before. It's always a normalised IP string, and may be IPv6.
   - In the current docker-compose setup, browser traffic still arrives as a
     private Docker IP (`172.x`). Your `detect_vpn_proxy()` scores that as
     VPN with 0.7 confidence. That behaviour isn't new, but **the backend now
     officially treats private IPs as on-campus** (course rule). Consider
     whether private ranges should still count toward VPN risk, or whether a
     private IP should be neutral. That's your call; flag it if you want us
     to send anything extra.
2. **Out-of-Singapore check-ins never reach you.** They're rejected before
   any face, liveness or risk call, so you'll see slightly fewer calls.
3. **Expect more simultaneous calls.** The backend now handles 100+
   concurrent check-ins without stalling
   ([section 11](#11-performance-and-stability)), so during the hidden
   stress tests your service may receive many `/liveness/check`,
   `/face/verify` and `/risk/assess` calls at once. The backend waits at
   most 5 s per call, then falls back without you. Worth load-testing your
   service with ~50–100 parallel requests.
4. **Base64 with line breaks:** a photo whose base64 contains newlines
   makes `/face/verify` report a mismatch. Browsers don't add them, so it's
   low priority, but stripping whitespace before decoding would make it
   robust.
5. **Dependency pins (from the re-released starter):** the starter now also
   caps `opencv-python<4.12` and `numpy<2` alongside the
   `mediapipe==0.10.18` pin you already have. Neither cap is in
   `module3-face-recognition/requirements.txt` or the root
   `requirements-test.txt` yet. Recommended, so a fresh install can't pull
   an incompatible OpenCV/NumPy pair.

## For Module 4 — Observability Dashboard

### New Prometheus metrics (`GET /metrics`)

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `account_lockouts_total` | Counter | — | Accounts locked after 10 consecutive failed logins |
| `checkin_rejected_geo_total` | Counter | `reason` = `ip` \| `gps` \| `gps_and_ip` | Check-ins rejected as outside Singapore |
| `security_violations_total` | Counter | `violation_type` (see [section 9](#9-audit-log-changes)) | Every `security_violation` audit event *(new in sections 7–11)* |

- `checkin_rejected_geo_total{reason=…}` series **only appear after the
  first rejection for that reason**. Panels should handle "no data" as 0
  (e.g. `or vector(0)` / Grafana "null as zero").
- Example PromQL:
  ```promql
  increase(account_lockouts_total[1h])
  sum by (reason) (increase(checkin_rejected_geo_total[1h]))
  # share of check-in attempts rejected for location
  sum(increase(checkin_rejected_geo_total[1h])) / sum(increase(checkin_attempts_total[1h]))
  ```

### Existing metrics: changed meaning

| Metric | Change |
|---|---|
| `login_failed_total` | Now also counts login attempts **blocked by a lockout**, not just wrong passwords |
| `checkin_attempts_total` | Includes geo-rejected attempts (it's incremented before validation, so it always did count rejected attempts) |

All other metric names and labels are unchanged.

### New audit log events (`GET /api/v1/audit/`, `GET /api/v1/audit/summary`)

| `action` | `success` | `resource_type` | `details` |
|---|---|---|---|
| `account_locked` | `false` | `user` | `{ "failed_attempts": 10, "lockout_minutes": 15 }` |
| `login_failed` (existing action, new variant) | `false` | — | `{ "reason": "account_locked" }` for attempts on a locked account |
| `checkin_rejected_geo` | `false` | `session` | `{ "reason": "ip"\|"gps"\|"gps_and_ip", "gps_in_singapore": bool, "ip_country": "US"\|null }` |
| `security_violation` | `false` | `user` / `session` / `checkin` | `{ "violation_type": "...", ... }` (see [section 9](#9-audit-log-changes)) |
| `checkin_approved` / `_flagged` / `_rejected` (existing) | — | `checkin` | now also `"risk_level": "LOW"\|"MEDIUM"\|"HIGH"\|"CRITICAL"` |
| `retention_sweep_run` (existing) | `true` | `retention` | now also written **hourly** with `"trigger": "scheduled"` (no `user_id`) |

- `checkin_rejected_geo` deliberately **doesn't** store the student's raw
  coordinates (privacy). `ip_country` is set only when the IP was the reason.
- These appear automatically in `/audit/summary`'s `by_action` breakdown.
- `ip_address` on all audit rows now follows the `X-Forwarded-For` rule
  ([section 3](#3-client-ip-now-honours-x-forwarded-for)).

### New `risk_factors` types

Check-ins and `GET /checkins/flagged` can now include `face_match_failed`,
`face_match_unverified` and `liveness_unverified` (see
[section 6](#6-face-match-and-liveness-are-enforced-when-required)), plus
`replay_suspected`, `gps_spoof_suspected`, `rapid_succession` and
`unusual_time` (see [section 7](#7-suspicious-check-ins-are-detected)). If
you chart risk factors by type, add them to your mapping. Severity
`"critical"` now always means "this alone rejected the check-in".

**Other things for the dashboard:**
- **Alerting:** `security_violation` events and
  `security_violations_total{violation_type}` are the simplest single source
  for a "suspicious activity" panel or alert.
- **Bands:** to show "auto-approved with logging" (MEDIUM), read
  `details.risk_level` from the outcome audit event rather than re-deriving
  bands from the score.
- **Audit log is read-only for everyone:** if any of your scripts or seed
  data delete or edit `audit_logs` rows directly, they will now fail.
- **Page size:** you already request `limit=100`, which is the new maximum,
  so nothing changes.
- **Known bug in the dashboard (unrelated to this release):** the session
  detail tiles read `flagged_count` / `flagged_checkins`, but
  `GET /stats/sessions/{id}` returns them inside `by_status`
  (e.g. `by_status.flagged`), so those tiles always show 0
  (`module4-observability/app/main.py:253, 296`).

### Not affected

Geo-rejected check-ins create **no check-in row**, so they don't appear in
`/stats/*`, `/export/*`, or check-in lists. They're only visible via the
metric and audit log above. If you want a "blocked check-ins" widget,
build it from those.

## Deploying this version

Anyone running the stack after this merges:

```bash
docker compose up -d --build backend                 # new dependency + bundled GeoIP data
docker compose exec backend alembic upgrade head     # new migration: account lockout columns
```

The migration is **not** run automatically on container start. Skipping it
makes every login fail with a database error. Current head:
`b7e2c4a91f03`.

**Sections 7–11 add three more migrations** (audit-log protection, photo
hash, device-fingerprint hash). Same two commands after pulling; the head
becomes `e8b2f4d61a90`. Skipping them makes every check-in fail.

## New error codes at a glance

| Status | `code` | Endpoint | Meaning |
|---|---|---|---|
| 429 | `ACCOUNT_LOCKED` | `POST /auth/login` | Account locked; see `Retry-After` |
| 403 | `OUTSIDE_SINGAPORE` | `POST /checkins/` | GPS or public IP is outside Singapore |

## Try it yourself

```bash
# Lockout: 10 wrong passwords, then the correct one → 429
for i in $(seq 1 10); do
  curl -s -o /dev/null -w "%{http_code} " -X POST localhost:8000/api/v1/auth/login \
    -H 'Content-Type: application/json' -d '{"email":"you@test.edu","password":"wrong"}'
done
curl -i -X POST localhost:8000/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"you@test.edu","password":"<correct>"}'

# Singapore rule: a foreign IP via X-Forwarded-For → 403 (needs an active session you're enrolled in)
curl -i -X POST localhost:8000/api/v1/checkins/ -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -H 'X-Forwarded-For: 8.8.8.8' \
  -d '{"session_id":"<id>","latitude":1.3483,"longitude":103.6831,"device_fingerprint":"dev1"}'
```
